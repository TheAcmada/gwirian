Gwirian · vision produit Synthèse d’échange — 8 juillet 2026

Au-delà de la v1 : de la gestion de tests BDD à la spec vivante et vérifiée

Point de départ : aller au-delà du produit en cours de développement et chercher une différenciation réelle face au marché — ouverte, IA-native — en étant très critique sur l’existant, pivot complet autorisé.

« Gwirian ne gère plus des tests BDD : c’est l’endroit où humains et agents s’accordent sur ce que le logiciel doit faire — et vérifient qu’il le fait toujours. »

La thèse issue de l’échange — les issues portent le delta, Gwirian porte l’intégrale
01 · Marché

Le marché historique meurt, la vague qui monte n’a pas de maison

Le créneau « plateforme de gestion BDD » a été invalidé publiquement. SmartBear a tenté 4 ans de commercialiser Cucumber via CucumberStudio : échec assumé, Cucumber rendu à la communauté fin 2024, domaine cucumber.io éteint en mars 2025. Le récit dominant des vendors est même « Cucumber is dead ». Le test management classique (TestRail, Xray, Zephyr) reste un silo QA Jira-centrique à l’IA cosmétique ; testomat.io est le concurrent moderne le plus proche.

La vraie vague 2025-2026 est le spec-driven development (GitHub Spec Kit — 90 000+ étoiles —, AWS Kiro, Tessl, OpenSpec) : la spec devient l’artefact premier, le code un output régénérable par les agents. Or l’analyse critique de ces outils (Martin Fowler) pointe le même angle mort : des tonnes de markdown sans cycle de vie, aucune collaboration d’équipe, aucune place pour les PM, aucune stratégie de vérification. Les specs SDD naissent dans un repo, ne sont jamais confrontées au produit réel, et meurent.

L’angle mort

Personne n’a construit la maison où ces specs vivent, se partagent et se vérifient. C’est exactement la forme de Gwirian.

02 · Critique de l’existant

Un beau produit de 2018, un châssis de 2026

Ce qui ne tient pas

  • Le cœur actuel est un CucumberStudio plus propre — la reconstruction soignée d’un produit dont le marché vient de mourir.
  • Les exécutions saisies à la main sont périmées à la seconde où elles sont créées : la CI possède déjà cette donnée, en mieux.
  • Pas de sync git — les specs des équipes BDD vivent dans les repos ; sans sync bidirectionnelle, la plateforme est un second silo (la cause exacte de l’échec de CucumberStudio).
  • Elasticsearch : complexité opérationnelle disproportionnée qui pénalise le self-host (Postgres FTS suffirait).
  • La licence O’Saasy n’est pas OSI : assumer « source-available » ou corriger.

Les actifs du pivot

  • Serveur MCP en full CRUD sur features, scénarios et exécutions, tokens scopés par workspace — rare : les MCP de TestRail/Xray sont des wrappers tiers.
  • Le champ context projet (URLs, comptes de test) — déjà pensé pour l’exécution par agent.
  • Modèle de données propre et hiérarchique, produit léger, keyboard-first.
  • Open core déjà séparé (saas/), self-hostable.
Verdict

Pivoter le positionnement, garder le châssis. « BDD feature management » n’a pas d’avenir — mais ~70 % du code construit sert le positionnement qui, lui, a le vent dans le dos.

03 · Axes stratégiques

Trois axes, classés par conviction

Axe 1 — Le système de référence des specs pour l’ère des agents

Conviction forte · retenu

Le « GitHub des specs » : la source de vérité collaborative que les agents (Claude Code, Cursor, Kiro, Spec Kit) lisent avant d’implémenter et mettent à jour après.

Cible
Le duo tech lead + PM des équipes en coding agentique — pas le QA manager.
Pourquoi nous
MCP full CRUD déjà là ; Gherkin est le seul format de spec lisible par un PM et vérifiable par une machine.
On jette
Le positionnement test management, la saisie manuelle comme flux principal, Elasticsearch, la rigidité Gherkin-only.
Premier chantier
La sync git bidirectionnelle + cycle de vie des specs, puis les adaptateurs d’import Spec Kit / OpenSpec.
Fragilité
Les devs considèrent que git est leur plateforme ; si la sync n’est pas irréprochable, « un dossier specs/ » gagne.

Axe 2 — La boucle de vérification agentique

Conviction moyenne-forte · le moat à 12 mois

Chaque scénario devient un contrat qu’un agent navigateur exécute réellement contre le produit déployé : « le produit fait-il encore ce que nous avons dit ? », indépendamment des tests écrits par l’agent qui a écrit le code.

Pourquoi nous
Le modèle d’exécution existe, le champ context aussi ; les incumbents ne suivront pas (cannibalise leurs sièges de testeurs).
Modèle
Le run d’agents = le SaaS payant ; la spec = open source. Résout élégamment la tension open core.
Fragilité
Coût et flakiness de l’exécution par agent ; des acteurs financés attaquent l’exécution — mais aucun ne possède la spec.

Axe 3 — La mémoire produit partagée humains-agents

Pivot radical · horizon, pas premier mouvement

Abandonner le cadre test/BDD : le « cerveau produit » interrogeable par MCP — intentions, décisions, comportements attendus.

Fragilité
Catégorie inexistante à évangéliser seul, frontière floue avec Notion/Linear, et on abandonne le seul avantage défendable : la vérifiabilité. C’est l’horizon où l’axe 1 s’élargit s’il réussit.
04 · L’objection décisive

« Les issues GitHub font déjà ça » — non, et voici pourquoi

Le workflow type (skills de Matt Pocock : to-spec → issue, to-tickets → tickets tracer-bullet, triage → machine à états) est excellent pour le flux de changement, et Gwirian ne le battra pas sur ce terrain. Mais quatre failles structurelles :

  • Une issue décrit un delta, jamais l’état. Fermée, elle devient de l’archéologie. « Que se passe-t-il quand le magic link expire ? » est éparpillé entre l’issue #47 qui a créé le comportement, la #212 qui l’a amendé et la #389 qui le contredit. La somme des issues n’est pas une spec — c’est un historique de diffs sans intégrale.
  • Une issue fermée ne prouve rien. « Closed » = « mergé un jour », pas « encore vrai ». Un scénario Gwirian porte un statut de vérification daté et situé.
  • Économie de contexte pour les agents. Chercher dans les issues = full-text dans un mélange de bugs, chores et specs périmées, 40 issues à charger. Un store structuré via MCP = « les 6 scénarios actifs du checkout, avec leurs steps ».
  • Deux frontières infranchissables : le multi-repo (le comportement produit traverse front, back, mobile ; les issues sont scopées par repo) et les non-développeurs (un PM ne lira jamais le produit à travers des issues fermées).
Conséquence sur le positionnement

Gwirian ne concurrence pas les issues, il s’y branche : les issues portent le delta, Gwirian porte l’intégrale. Quand un ticket ship, l’agent absorbe le delta dans le contrat courant via MCP, puis il est vérifié.

D’où la définition validée ensemble : Gwirian est la spec fonctionnelle complète, courante (un état maintenu, pas un cumul) et continuellement vérifiée (c’est ce qui la distingue d’un dossier docs/ ou d’un Notion qui dérivent en silence) du produit — limitée aux comportements observables ; le « pourquoi » reste dans les ADRs et le tracker.

05 · Structure de la spec

Trois couches, trois régimes de vérité

Les scénarios seuls font une suite de tests, pas une spec : un Given/When/Then est un exemple ; une spec est faite de normes. La pièce centrale manquante est la Règle — énoncé normatif court et falsifiable (« Un magic link expire après 15 minutes ») — que Gherkin supporte nativement (Rule:, v6+) et qui outille enfin l’Example Mapping.

Workspace (= le produit)
└── Domaine                ~10-30, stables (Auth, Facturation…)
    ├── Glossaire           entités, définitions, états & cycles de vie
    ├── Acteurs             rôles et ce qui les distingue
    └── Feature             une capacité
        ├── Intention       le « pourquoi » en 2 phrases + liens (issues, ADRs)
        ├── Règles          les énoncés normatifs ← le cœur manquant
        │   └── Scénarios   les exemples qui illustrent chaque règle
        │       └── Exécutions  les preuves
        ├── Questions ouvertes
        └── Statut          draft → approuvée → implémentée → vérifiée → dépréciée
CoucheContenuRégime de vérité
VocabulaireGlossaire, acteurs, étatsCohérence — lint sémantique par agent : termes définis, transitions légales, orphelins.
NormativeRèglesCouverture & non-contradiction — chaque règle illustrée par ≥ 1 scénario ou marquée non-exécutable ; détection de contradictions par agent.
IllustrativeScénariosExécution — CI ou agent, avec preuves datées.

Deux choix de périmètre : l’intention est un pointeur, pas un contenu (la frontière avec l’axe 3) ; matrices de permissions et machines à états sont des vues dérivées des règles, générées, jamais maintenues à la main. Et c’est la bonne granularité pour les agents : glossaire + règles du domaine = quelques centaines de tokens denses, puis 3-4 scénarios pour les cas limites.

06 · Exécution & CI

Gwirian n’exécute pas — il est le registre des preuves

Préalable : l’ancrage. Un ID stable porté par le Gherkin lui-même (@gwirian-6f3a2b) — survit au rebase et au déplacement, reste du Gherkin pur. C’est le point où CucumberStudio s’est cassé les dents.

Canal 1 — CI : ingestion des résultats existants

repo (.feature + glue)
   │  CI run (job de test inchangé)
   ▼
rapport (Cucumber Messages / JSON, JUnit XML, Playwright)
   │  gwirian push --report cucumber.ndjson --sha $SHA --env staging
   ▼
Gwirian : exécutions en batch, rattachées par @gwirian-id
          chaque preuve porte SHA + branche + environnement + date

« Passed » devient un énoncé daté et situé : conforme sur main@f2e9f6f en staging, mardi. Toute équipe Cucumber/Playwright a de la valeur immédiate sans changer ses tests — la porte d’entrée adoption.

Canal 2 — Agent : la longue traîne

Pour les scénarios qui ne méritent pas de glue code : un orchestrateur lit le champ context, joue le Given/When/Then via agent navigateur, dépose une exécution avec preuves (screenshots, trace, verdict). À la demande, en cron, ou après déploiement. Le canal différenciant — et le produit payant.

Canal 3 — La CI gardienne de la spec (sens inverse)

Un check de PR qui répond à trois questions : impact (« cette PR affecte 4 scénarios : 3 vérifiés, 1 jamais re-vérifié »), couverture (comportement nouveau sans mise à jour de spec ?) et cohérence (les règles modifiées contredisent-elles l’existant ?).

Chaque scénario porte alors un mode de vérification (automatisé, agent, manuel, non vérifié) et une fraîcheur relative au code — le tableau de bord de santé de la spec est calculé depuis les preuves, plus déclaratif.

  1. Tags d’ancrage + endpoint d’ingestion batch (SHA/env en champs de première classe).
  2. CLI gwirian push + GitHub Action / composant GitLab CI.
  3. Le check de PR (impact, couverture, cohérence).
  4. L’orchestrateur d’agents — en dernier : le plus dur, et il gagne à s’appuyer sur des trous de couverture déjà visibles.
07 · Prochain pas

Valider à coût quasi nul, cette semaine

Dogfooding : développer Gwirian avec Gwirian. Écrire la spec de la prochaine fonctionnalité comme règles/scénarios dans Gwirian, brancher le MCP local sur Claude Code, et imposer le flux : l’agent lit la spec avant d’implémenter, implémente, vérifie, écrit l’exécution. Variante encore plus petite : un skill sync-contract (~une session) qui, au ship d’un ticket du workflow Pocock existant, absorbe le delta dans le contrat courant via MCP.

Critère de décision

Deux semaines d’usage : si la vue « contrat courant vérifié » n’apporte rien que le tracker n’apportait pas, l’axe 1 est réfuté à peu de frais. Si elle apporte, le mode d’emploi devient le premier récit marketing : « ça complète votre workflow d’issues, ça ne le remplace pas ».
